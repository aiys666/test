# 额度策略分析框架（方法论）

八模块分析框架，所有指标必须在 SQL 内闭环产出（对比/差值在 SQL 同表条件聚合或自连接完成，避免脱离口径的二次计算）。分子分母同粒度，策略灰度按时间分段（8/10-9/3 为 70/30，9/3 后为 30/70，勿用单一权重）。

## 模块总览

| 模块 | 核心问题 | 主要数据源 | 关键指标 |
|---|---|---|---|
| 1 额度供给 | 发了多少额度（主额/在线/离线） | yj + yuhan底表 | 授信均值、tag1发放量、批次发放人数/金额 |
| 2 使用效率 | 额度有没有被用、怎么用 | yj + funnel | TR、渗透率、使用率、件均、临额使用四指标 |
| 3 在线策略 | V5_2/V5_3 效果差异 | yj strategy_flag×tag | 三阶段×flag×tag 全套指标 |
| 4 离线策略 | 8/24 准入收紧效果 | yuhan底表 + change_record | 批次逾期分布、C013/C015 周度坏账 |
| 5 风险分层 | 坏账在谁身上 | yj | 评级档×四组、评分档、产品期限 t0/t7/t30 |
| 6 客群质量 | 客群是否在变差 | yj | 评级迁徙、多头逾期、复贷周期、循环过期 |
| 7 性价比因果 | 策略净收益与因果 | yj hash 三组 | DID、放款/息费/坏账/净收益、单位额度产出 |
| 8 发放起点漏斗 | 发出去的额度兑现了多少 | `mx.yj_temp_grant_funnel_v11` | 发放→进件→用信→放款→用额 五层人数/件数/金额、兑现率 |

## 1. 额度供给

- 主额度：复贷 `credit_amount`；首贷 `credit_amount_sx`（首贷批后即借满，TR 80%+，不可与复贷比）
- 在线供给：`temp_credit_amount_issue_tag=1` 笔数/渗透率；实际使用看 temp_grant_amount>0
- 离线供给：底表按 temp_limit_tag 批次聚合 people/issue_amount；一个 mid 可在多批次，分析时按批次+mid 去重
- 供给健康度：发放金额/主额度比、发放间隔 last_temp_credit_amount_issue_day_gap

## 2. 使用效率（TR 体系）

- TR 动支率 = 放款金额 / 授信额度（复贷 27-34%）；勿与审批通过率（放款笔数/进件笔数，复贷 60-65%、首贷 8-10%）混淆
- 在线临额渗透率 = tag1 笔数 / 放款笔数
- 在线临额使用率 = temp_grant_amount>0 笔数 / tag1 笔数（弹窗后实际接受比例）
- 离线临额使用率 = 底表 curr_temp_used_credit_limit / curr_temp_credit_limit
- 件均拆分：real_issue_amount（总件均）vs 主额件均 vs 临额件均，判断策略拉动来自人数还是单价

## 3. 在线策略三阶段（V5_2/V5_3）

- P0 <8/10：无分桶（旧策略）
- P1 8/10-9/3：70% V5_3（hash≤0.7）
- P2 9/3-9/22：30% V5_3（hash≤0.3）
- P3 ≥9/22：V6_1 拒尾干扰期，策略对比需单列

每阶段 × flag × tag 输出：笔数、TR、件均、t0、使用临额均值/件数/总额、评级均值。
解读要点：tag0（未发）组是策略决策"拒绝"的客群，tag1 是实际发放客群；同 flag 内 tag1 vs tag0 反映模型选人能力，跨 flag 的 tag1 vs tag1 才反映策略门槛差异。

## 4. 离线政策（8 月底准入收紧，按批次验证勿用笼统日期）

- 底表 `id_30days_max_overdue_days`：验证准入口径。精确批次证据（按 temp_limit_tag 的 issue_to）：
  - 有在贷批次：8/14 的 0826 批次 pct_ovd1_2 仍有 7.7-10.1%、8/21 的 0902 批次 11.1%；**8/29 的 0909 批次起降为 0**，pct_ovd0 升至 94.6-98.1%
  - 无在贷批次：8 月 pct_ovd1_2 5.5-9.2%（0806/0813/0820/0827），9/2 的 0903 批次仍有 5.8%，**9/9 的 0910 批次起降为 0**
  - 无在贷批次该字段约 1/3 为 null，pct_ovd0 天然只有 60% 左右，收紧效果只比 pct_ovd1_2，不比 pct_ovd0
- change_record C013/C015 打标按周×评级：笔数、件均、TR、t0、多头；四组互斥口径用"末次 TEMP 事件"
- 底表批次分组命名含"有在贷/无在贷/减息/对照组"，分析时先归类再比较；issue_from 为多快照最小日期无业务含义，用 issue_to 定批次时间

## 5. 风险分层

- 三维交叉：阶段/周 × 四组（none/offline/online_tag0/online_tag1）× 评级档（1-5/6-8/9+）
- 账龄：t0（首期到期）→ t7 → t30（终损，本金 capit 与利息分开）。产品最长 28 天，t0 全成熟需放款周+4-5周；t30 需 +6 周以上，未成熟留空不外推
- 结构分解：率效应 Σ(w1×(r1-r0)) + 结构效应 Σ(r0×(w1-w0))；算术贡献≠因果

## 6. 客群质量

- 评级：fd_creditlevel_main_v4_2 分档占比 + 均值
- 共债：curr_ovd_cnt_all 均值、≥1 占比（多头逾期是 2026-08 客群恶化的最强领先信号）
- 复贷深度：loan_cycle 分层（<5/5-10/10-20/20+）
- 循环额度过期：is_loop_limit_expired=1 占比（过期老客坏账 57-62%）
- 同期对照：被政策覆盖组（offline 多头）与未覆盖组（none 多头）趋势分叉，可识别政策外恶化

## 7. 因果识别（hash 自然实验 DID）

三组：A hash>0.7（始终V5_2，平行对照）、B 0.3<hash≤0.7（P1执行V5_3、P2切回，实验组）、C hash≤0.3（始终V5_3）。

- 全客户 DID = (B_P2-B_P1) - (A_P2-A_P1)：回答"策略对大盘坏账的因果效应"
- tag1 桶 DID：回答"切回后临额客群池质量变化"
- 验证平行趋势：P0 各组坏账率差值（C-A 基线偏差已知存在，需在结论中标注上界）
- 性价比表：放款金额变化、息费（equal_houshou_should_interest/funnel.fact_interest）、坏账金额变化、净收益、TR 变化，全部用组间实际差值不用假设

## 8. 发放起点漏斗（临额供给侧，2026-10-25 落库）

**问题**：以「发放」为起点看，发出去的临额到底被多少人看到、多少人进件、多少人真的用上、最后兑现多少金额。
**表**：`mx.yj_temp_grant_funnel_v11`（一行 = 一次发放）。**SQL**：`scripts/临额发放起点_漏斗取数SQL_v11_20261025.sql`。

### 8.1 五层定义（每层都要给人数 / 件数 / 金额）

| 层 | 定义 | 判定字段 |
|---|---|---|
| L1 发放 | 一次发放事件（离线=mid×C015 时刻；在线=biz 的 1386 tag=1 且 857 额>0） | `grant_time` / `grant_amount` |
| L2 进件 | 该次发放之后出现的申请 | `is_app_after_grant`（`app_time >= grant_time`） |
| L2' 有效期内进件 | 上述进件中，进件落在有效期内 | `is_app_in_win`（`app_time BETWEEN grant_time AND expire_time`） |
| L3 用信 | 进件走到「确认用信」（额度冻结那一刻） | `is_use_after_grant`（`apply_time IS NOT NULL AND app_time >= grant_time`） |
| L3' 有效期内用信 | 用信确认时刻落在有效期内 | `is_use_in_win` |
| L4 放款 | `if_issue = 1` | `n_issue_all` / `n_issue_win` |
| L5 用掉临额 | 本笔真实消耗了临额 | `used_amt > 0`（离线取 `offline_used_this` 且严格匹配批次；在线取 `online_used_this`） |

**子集单调必须成立**：`n_app_win <= n_app_all`、`n_use_win <= n_use_all`、`n_use_win_used <= n_use_win`（断言 A5）。`apply_time` 有值才计用信，且必须 `app_time >= grant_time`，否则会出现「用信件数 > 进件件数」的伪结果。

### 8.2 维度

- `temp_type`：`offline` / `online`
- `grade_v5_3`：**发放时刻**评级的最近快照（`MAX_BY(value, createtime)`，`createtime <= grant_time`）；再折 `grade_band` = `1_高(1-2)` / `2_中(3-7)` / `3_低(8+)` / `unknown`
- `strategy_version`：仅在线，取 1523 落库标签（`temp_credit_amount_strategy_test_flag LIKE '%V5_3%'`）；离线恒 `NA`
- 汇总：§2 用 `GROUP BY ROLLUP (temp_type, grade_band)`、§3 用 `ROLLUP (strategy_version, grade_label)`；**评级 null 必须先映射成 `unknown` 再 ROLLUP**，否则与合计行标签撞车

### 8.3 两类漏斗的物理差异（禁止相加）

- **离线 = 先发后用**：发放挂在 **mid** 上，发放后等用户来申请；一次发放可被窗口内多笔进件消耗 → 发放 24,454 次 ≠ 进件 37,047 件，件数可大于发放次数
- **在线 = 边发边用**：发放挂在 **biz** 上（用信确认时才发），发放即绑定该订单 → 进件恒 = 发放、有效期进件恒 = 发放
- 因此「合计 40,692 次发放 / 16,738 人」只是两类事件并列，**不是统一的发放人数**；跨类型比较只能比「兑现率」这类比率，不能比绝对人数

### 8.4 关键指标

- **兑现率 `redeem_rate` = Σ used_amt / Σ grant_amount**（批次级口径，非笔级金额比）
- **放款转化 `issue_rate_by_cnt` = Σ n_issue_all / Σ n_app_all**（离线约 0.69、在线约 0.98）
- 有效期衰减：`n_app_win / n_app_all`、`n_use_win / n_use_all`——看额度有效期对转化损耗的贡献
