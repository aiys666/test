# 额度策略分析框架（方法论）

八模块分析框架，所有指标必须在 SQL 内闭环产出（对比/差值在 SQL 同表条件聚合或自连接完成，避免脱离口径的二次计算）。分子分母同粒度，策略灰度按时间分段（8/10-9/3 为 70/30，9/3 后为 30/70，勿用单一权重）。

## 模块总览

| 模块 | 核心问题 | 主要数据源 | 关键指标 |
|---|---|---|---|
| 1 额度供给 | 发了多少额度（主额/在线/离线） | yj + yuhan底表 | 授信均值、tag1发放量、批次发放人数/金额 |
| 2 使用效率 | 额度有没有被用、怎么用 | yj + funnel | TR、渗透率、使用率、件均、临额使用四指标 |
| 3 在线策略 | V5_2/V5_3 效果差异 | yj strategy_flag×tag | 三阶段×flag×tag 全套指标 |
| 4 离线策略 | 8/24 准入收紧效果 | yuhan底表 + change_record | 批次逾期分布、C013/C015 周度坏账 |
| 5 风险分层 | 坏账在谁身上 | yj | 评级档×四组、评分档、产品期限 t0/t7/t30 |
| 6 客群质量 | 客群是否在变差 | yj | 评级迁徙、多头逾期、复贷周期、循环过期 |
| 7 性价比因果 | 策略净收益与因果 | yj hash 三组 | DID、放款/息费/坏账/净收益、单位额度产出 |
| 8 发放起点漏斗 | 发出去的额度兑现了多少 | `mx.yj_temp_grant_funnel_v11` | 发放→进件→用信→放款→用额 五层人数/件数/金额、兑现率 |

## 1. 额度供给

- 主额度：复贷 `credit_amount`；首贷 `credit_amount_sx`（首贷批后即借满，TR 80%+，不可与复贷比）
- 在线供给：`temp_credit_amount_issue_tag=1` 笔数/渗透率；实际使用看 temp_grant_amount>0
- 离线供给：底表按 temp_limit_tag 批次聚合 people/issue_amount；一个 mid 可在多批次，分析时按批次+mid 去重
- 供给健康度：发放金额/主额度比、发放间隔 last_temp_credit_amount_issue_day_gap

## 2. 使用效率（TR 体系）

- TR 动支率 = 放款金额 / 授信额度（复贷 27-34%）；勿与审批通过率（放款笔数/进件笔数，复贷 60-65%、首贷 8-10%）混淆
- 在线临额渗透率 = tag1 笔数 / 放款笔数
- 在线临额使用率 = temp_grant_amount>0 笔数 / tag1 笔数（弹窗后实际接受比例）
- 离线临额使用率 = 底表 curr_temp_used_credit_limit / curr_temp_credit_limit
- 件均拆分：real_issue_amount（总件均）vs 主额件均 vs 临额件均，判断策略拉动来自人数还是单价

## 3. 在线策略三阶段（V5_2/V5_3）

- P0 <8/10：无分桶（旧策略）
- P1 8/10-9/3：70% V5_3（hash≤0.7）
- P2 9/3-9/22：30% V5_3（hash≤0.3）
- P3 ≥9/22：V6_1 拒尾干扰期，策略对比需单列

每阶段 × flag × tag 输出：笔数、TR、件均、t0、使用临额均值/件数/总额、评级均值。
解读要点：tag0（未发）组是策略决策"拒绝"的客群，tag1 是实际发放客群；同 flag 内 tag1 vs tag0 反映模型选人能力，跨 flag 的 tag1 vs tag1 才反映策略门槛差异。

## 4. 离线政策（8 月底准入收紧，按批次验证勿用笼统日期）

- 底表 `id_30days_max_overdue_days`：验证准入口径。精确批次证据（按 temp_limit_tag 的 issue_to）：
  - 有在贷批次：8/14 的 0826 批次 pct_ovd1_2 仍有 7.7-10.1%、8/21 的 0902 批次 11.1%；**8/29 的 0909 批次起降为 0**，pct_ovd0 升至 94.6-98.1%
  - 无在贷批次：8 月 pct_ovd1_2 5.5-9.2%（0806/0813/0820/0827），9/2 的 0903 批次仍有 5.8%，**9/9 的 0910 批次起降为 0**
  - 无在贷批次该字段约 1/3 为 null，pct_ovd0 天然只有 60% 左右，收紧效果只比 pct_ovd1_2，不比 pct_ovd0
- change_record C013/C015 打标按周×评级：笔数、件均、TR、t0、多头；四组互斥口径用"末次 TEMP 事件"
- 底表批次分组命名含"有在贷/无在贷/减息/对照组"，分析时先归类再比较；issue_from 为多快照最小日期无业务含义，用 issue_to 定批次时间

## 5. 风险分层

- 三维交叉：阶段/周 × 四组（none/offline/online_tag0/online_tag1）× 评级档（1-5/6-8/9+）
- 账龄：t0（首期到期）→ t7 → t30（终损，本金 capit 与利息分开）。产品最长 28 天，t0 全成熟需放款周+4-5周；t30 需 +6 周以上，未成熟留空不外推
- 结构分解：率效应 Σ(w1×(r1-r0)) + 结构效应 Σ(r0×(w1-w0))；算术贡献≠因果

## 6. 客群质量

- 评级：fd_creditlevel_main_v4_2 分档占比 + 均值
- 共债：curr_ovd_cnt_all 均值、≥1 占比（多头逾期是 2026-08 客群恶化的最强领先信号）
- 复贷深度：loan_cycle 分层（<5/5-10/10-20/20+）
- 循环额度过期：is_loop_limit_expired=1 占比（过期老客坏账 57-62%）
- 同期对照：被政策覆盖组（offline 多头）与未覆盖组（none 多头）趋势分叉，可识别政策外恶化

## 7. 因果识别（hash 自然实验 DID）

三组：A hash>0.7（始终V5_2，平行对照）、B 0.3<hash≤0.7（P1执行V5_3、P2切回，实验组）、C hash≤0.3（始终V5_3）。

- 全客户 DID = (B_P2-B_P1) - (A_P2-A_P1)：回答"策略对大盘坏账的因果效应"
- tag1 桶 DID：回答"切回后临额客群池质量变化"
- 验证平行趋势：P0 各组坏账率差值（C-A 基线偏差已知存在，需在结论中标注上界）
- 性价比表：放款金额变化、息费（equal_houshou_should_interest/funnel.fact_interest）、坏账金额变化、净收益、TR 变化，全部用组间实际差值不用假设

## 8. 发放起点漏斗（临额供给侧，2026-10-25 落库）

**问题**：以「发放」为起点看，发出去的临额到底触达多少人、多少人进件、多少人真的用上、最后兑现多少金额；**且必须按「发放时刻的用户等级」拆开**，否则会把「优质档发得多但用不掉」和「低档发得少却用满」混成一个平均数。
**表**：`mx.yj_temp_grant_funnel_v11`（40,692 行 = 一次发放一行）。**SQL**：`scripts/临额发放起点_漏斗取数SQL_v11_20261025.sql`。**交付**：`墨西哥/放款资产额度指标/临额发放起点_分等级分析_20260901_1021.xlsx`。

### 8.1 五层定义（每层都要给人数 / 件数 / 金额）

| 层 | 定义 | 明细表列 |
|---|---|---|
| L1 发放 | 一次发放事件（离线=mid×C015 时刻；在线=biz 的 1386 tag=1 且 857 弹窗额>0） | `grant_time` / `grant_amount` |
| L2 进件（归属） | 事件时刻之前最近一次发放「接住」的申请；事件时刻=`COALESCE(apply_time, app_time)` | `n_app_all` |
| L2a 发放后进件 | 上述中 `app_time >= grant_time`（严格漏斗分子） | `n_app_after` |
| L2b 发放前进件 | `app_time < grant_time` 但 `apply_time >= grant_time`（跨天笔，离线 2,697 件） | `n_app_before`（诊断） |
| L2' 有效期内进件 | `app_time BETWEEN grant_time AND expire_time` | `n_app_win` |
| L3 用信 | `apply_time IS NOT NULL`（额度冻结那一瞬） | `n_use_all` |
| L3' 有效期内用信 | `apply_time BETWEEN grant_time AND expire_time`（**锚点是 apply_time，不是 app_time**） | `n_use_win` |
| L3+ 有效期内用信且真实用额 | 上一行 ∩ `used_amt > 0` —— 即「有效期内在用信里真的动了临额」 | `n_use_win_used` |
| L4 放款 | `if_issue = 1`；金额 = `contract_amount` | `n_issue_all` / `n_issue_win` / `contract_amt_all` / `contract_amt_win` |
| L5 用掉临额 | 本笔真实消耗临额金额（离线 `offline_used_this` 且 `offline_grant_time = 本批次`；在线 `online_used_this`） | `used_amt_all` / `used_amt_win` |

**子集单调必须成立**（断言 A5 六项全 0）：`n_app_win <= n_app_all`、`n_use_win <= n_use_all`、`n_use_win_used <= n_use_win`、`n_used_win <= n_used_all`、`n_issue_win <= n_issue_all`、金额同理。

**⚠️ 两个锚点不能混用**：`app_time`（用户提交申请）与 `apply_time`（确认用信/额度冻结）可相差数天（实测 p99 5,002 秒、最长 65 小时）。「进件」用 `app_time`、「用信」必须用 `apply_time`。混用会出现「有效期内用信件数 > 有效期内进件件数」的伪结果（离线含跨天版即如此：17,838 > 16,947）——**报告里必须注明是「含跨天」还是「严格嵌套」**。

### 8.2 维度（评级必须双源，不可一套打两类）

- `temp_type`：`offline` / `online`（**不可相加**，见 8.3）
- **离线评级**：`mx.android_oldcust_maincreditlevel_charge_v5_3_table` 按 mid 取 `MAX_BY(值, createtime)` 且 `createtime <= grant_time`（发放时刻的最近 V5_3 快照，T0 11 点批次）
- **在线评级**：`ods.s21_risk_model_record` **本 biz** 的节点 **1500=V5_2 / 1542=V5_3**（`strategytype='CHAMPION'`）；按 `strategy_version` 选用，得到 `grade_used`
- `grade_band`：`1_高(1-2)` / `2_中(3-7)` / `3_低(8+)` / `unknown`
- `strategy_version`：仅在线，取 1523 落库标签（`temp_credit_amount_strategy_test_flag LIKE '%V5_3%'`）；离线恒 `NA`
- 汇总：§2 `GROUP BY ROLLUP (temp_type, grade_band)`、§3 `ROLLUP (strategy_version, grade_label)`；**null 评级先映射成 `unknown` 再 ROLLUP**，否则会和合计行标签撞车
- 值域差异：V5_2 1~16、V5_3 1~13 —— 跨版本只能比同一「档位语义」或比 band，不能直接比原始 grade 数字

### 8.3 两类漏斗的物理差异（禁止相加）

- **离线 = 先发后用**：发放挂在 **mid** 上，发完等用户来申请；一次发放可被窗口内多笔进件消耗 → 发放 24,454 次 ≠ 进件 39,741 件（件数 > 发放次数）
- **在线 = 边发边用**：发放挂在 **biz** 上（确认页才发），发放即绑定该订单 → 进件恒 = 发放、有效期进件恒 = 发放
- 因此「合计 40,692 次发放 / 16,738 人」只是两类事件并列，**不是统一的发放人数**；跨类型只能比「兑现率 / 转化率」这类比率，不能比绝对人数

### 8.4 指标字典（人数 / 件数 / 金额三层齐备）

| 指标 | 公式 | 读法 |
|---|---|---|
| 触达率 | `mid_app / grant_mid` | 发放的人里有多少回来进件（离线才有意义，在线恒 100%） |
| 有效期内触达率 | `mid_app_win / mid_app` | 额度有效期对「回访」的损耗 |
| 进件→用信 | `use_cnt / app_cnt` | 本窗口恒 ≈100%（归属进件全有 apply_time），**不建议单独讲** |
| 用信→真实用额 | `use_cnt_win_used / use_cnt_win` | **核心**：用信了却没动临额，说明主额够用 |
| 放款转化 | `issue_cnt / app_cnt` | 离线 ≈0.69、在线 ≈0.98 |
| 临额占合同比 | `used_amt / contract_amt` | 临额在成交金额里的比重 |
| **兑现率** | `Σ used_amt / Σ grant_amount` | **批次级**口径，非笔级金额比；离线 ≤100%（断言 A4 允许 122 笔超发，见 8.6） |
| 有效期兑现率 | `Σ used_amt_win / Σ grant_amount` | 只在有效期窗口内算 |
| 人均 | `金额 / 人数`、`件数 / 人数` | 判断拉动来自人数还是单价 |

### 8.6 口径陷阱清单（发放起点专属）

1. **评级不能一套打两类**：离线用 V5_3 快照、在线用本 biz 的 1500/1542；混用会把不同值域的等级塞进同一个档位
2. **不能只取「当前评级」**：必须是发放时刻之前的最近快照，否则赛后评级漂移会污染分组
3. **`n_app_all` 不能要求 `app_time >= grant_time`**：否则「白天进件、晚上发放后确认」的 2,697 笔会被归属成功却计成 0（v11 的丢数 bug）
4. **「用额 > 发放额」是机制不是错误**（断言 A4 = 122 笔 / 4.99 万 / 占离线用额 1.3%）：离线批次 5 天内可被多笔复用，并叠加账户内未过期的旧余额
5. **离线使用额必须按 `offline_grant_time = grant_time` 严格匹配批次**，否则同一 mid 的多批次会互相串额
6. **C013 必须剔除**：2,331 笔 / 193 万是 9 月手动补单异常，混入会虚增发放
7. **分档人数之和 ≥ 合计人数**：同一 mid 在不同发放时刻可能落在不同档，只有合计行是不重复人数
8. **断言的期望值写在 SQL §4**；任何一格偏离先查窗口（离线 C015 < 10-22、在线 `issue_date ≤ 10-21`）与 `apply_time` 是否被 `release_time` 兜底替换

### 8.7 分析叙事模板（结论怎么排）

1. **规模与结构**：两类各发多少（次数/人数/金额），重叠人数多少，不可相加
2. **漏斗衰减**：从触达 → 有效期内触达 → 用信用额 → 放款，每一跳掉多少人/多少件，定位损耗在哪一跳
3. **分档兑现**：高/中/低三档的「发放额 vs 兑现率」二维定位——谁发得多却用不掉、谁发得少却用满
4. **策略版本**：同评级下 V5_2 vs V5_3 的兑现差异，回答「放开档位到底有没有被用掉」
5. **收口建议**：优质档降额/缩短有效期 vs 低档提额/延长有效期，用「边际发放额 × 该档兑现率」估算转移收益
