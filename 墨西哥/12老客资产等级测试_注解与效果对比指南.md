## 一、这个测试在做什么（一句话）

墨西哥**老客复贷的"资产等级"模型在做 A/B 测试**——用随机分桶把老客分成"测试组（跑新版本模型）"和"冠军组（跑老版本模型）"，对比新旧版本在**通过率、放款、逾期、额度**上的差异，决定要不要全量切换新版本。

---

## 二、核心机制：随机分桶（A/B 测试的地基）

### 2.1 分桶公式（全表最关键的逻辑）

```sql
-- 把 手机号/证件号+app 哈希成一个 0~1 的随机数
from_base(substr(to_hex(sha256(to_utf8('20251217'||phone||app_group_sha256))),1,4),16)/65536.0
```

**原理**：`sha256(盐值+用户标识)` → 取前4位hex → 转成 0~65535 的整数 → 除以65536 → 得到稳定的 0~1 随机数。

- 同一个用户永远得到同一个数（**稳定分桶**，不会每次不同）
- 不同用户均匀分布（**随机分组**）
- 盐值（如 '20251217'）用来**换一批测试时重新分桶**

### 2.2 怎么用这个随机数分组

| 阈值 | 分组 | 含义 |
|------|------|------|
| 随机数 < 0.3 / 0.5 / 0.7 | **测试组** | 走新版本模型 |
| 随机数 ≥ 阈值 | **冠军组** | 走老版本模型 |

不同测试用不同阈值（30%测试/70%冠军、50/50、70/30），取决于测试规模。

## 三、版本演进时间线（v3_flag 字段）

这是理解整个测试的**时间轴**，代码里按 app_time 分层：

```
2025-07~08  V3_1 / V3_2 / V3_3（早期）
2025-08~09  V3_3 / V4（V4 上线）
2025-09~11  V3_3 / V4_2（V4_2 分桶测试）
2025-11~2026-02  V4_2 / V5_1
2026-03~04  V5_1 / V5_2
2026-04~05  V5_2
2026-05~06  V5_2 / V5_3
2026-06~08  V5_3
2026-08-20起 V6_1 vs V5_3  ← 最新测试（30% V6_1 / 70% V5_3）
```

**V2/V3 是历史基线，V4/V5/V6 是迭代版本**。每个新版本上线前，都会先分桶跑一段时间对比。

## 六、怎么看测试效果（对比方法论）

### 6.1 第一步：版本间对比（看哪个版本更好）

```sql
-- 对比不同资产等级版本的通过率、逾期率
SELECT v3_flag,
       count(*) AS cnt,
       count_if(if_sx_passed=1) * 1.0 / count(*) AS sx_pass_rate,   -- 授信通过率
       count_if(if_issue=1) * 1.0 / count(*) AS issue_rate,          -- 放款转化率
       count_if(if_issue=1 AND is_t30_overdue=1) * 1.0
           / count_if(if_issue=1 AND is_t30_window=1) AS t30_ovd_rate  -- T30逾期率
FROM mx.yj_test_table_250225
GROUP BY v3_flag
```

**判断标准**：新版本要满足 **通过率不降 or 提高 + 逾期率不升 or 降低**，才值得切换。

### 6.2 第二步：同版本 A/B 对比（排除时间干扰）

```sql
-- 只取 V5_3 vs V6_1 的分桶组（2026-08-20 起）
SELECT daily_max_limit_tag,
       count(*) AS cnt,
       count_if(if_sx_passed=1) * 1.0 / count(*) AS sx_pass_rate,
       count_if(if_issue=1 AND is_t30_overdue=1) * 1.0
           / count_if(if_issue=1 AND is_t30_window=1) AS t30_ovd_rate
FROM mx.yj_test_table_250225
WHERE v3_flag IN ('V5_3', 'V6_1')
GROUP BY daily_max_limit_tag
```

**关键**：同一时间段的测试组 vs 冠军组，人群随机，差异就是模型效果。

### 6.3 第三步：评分卡变量区分度（看变量有效性）

```sql
-- 看"多头数"这个变量的区分度：分不同的多头区间，看逾期率是否单调
SELECT advance_duotou_cnt_x_19_score,
       count(*) AS cnt,
       count_if(if_issue=1 AND is_t30_overdue=1) * 1.0
           / count_if(if_issue=1 AND is_t30_window=1) AS t30_ovd_rate
FROM mx.yj_test_table_250225
GROUP BY advance_duotou_cnt_x_19_score
ORDER BY advance_duotou_cnt_x_19_score
```

**判断标准**：好的变量 → 分数越低的区间，逾期率越高（单调性）。如果分数和逾期率没关系，这个变量就没用。

### 6.4 第四步：产品/额度策略测试

用 `product_test_0722`、`temp_limit_test_flag`、`cap_1point8_strategy_test_flag` 分组，对比各策略组的放款率、逾期率、件均。

## 八、注意事项（踩过的坑）

| 注意 | 说明 |
|------|------|
| **必须带版本/分组条件** | 表里混了所有版本，不 filter v3_flag 会混在一起看不清 |
| **逾期率要限窗口** | is_t30_window=1 才是有完整T30观察期的订单，否则分母不全 |
| **不同版本时间段不同** | V3 是2025年的，V6_1 是2026-08-20起的，直接比会混入时间因素，务必看同时间的 A/B 组 |
| **hash 分桶稳定** | 同一个用户不会变组，但换盐值会重新分桶，对比时用同盐值的分组标签 |
| **测试组/冠军组≠好坏** | 测试组只是"实验对象"，不代表"更好"，要看指标判断 |
