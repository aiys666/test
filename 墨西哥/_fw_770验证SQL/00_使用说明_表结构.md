# 770.4占用机制验证 SQL 脚本集合 —— 使用说明

## 📌 目录说明

本目录包含**13组独立可复跑的Presto SQL脚本**，按**探查链条顺序**排列，供逐步验证"存量占用/结清后残留"机制。所有脚本已从Python探查代码中提取，去除了f-string变量，直接可在Presto中执行。

## � 事件码语义完整映射表（基于《墨西哥循环额度》V1.5）

> ⚠️ **核心修正**：C004 和 C008 虽然 `change_action` 都是 `UNFREEZE_LIMIT`，但**触发条件和释放逻辑完全不同**！之前的冲突扫描只看动作没区分事件码，导致对"解冻"的理解不完整。

| 事件码 | 名称 | 触发条件 | 释放/冻结逻辑 | 对770.4结论的影响 |
|--------|------|---------|--------------|-----------------|
| **C003** | 用信冻结 | 客户成功提交用信 | 锁定额度 += 本次用信额度（**先主额再临时**） | 冻结来源 |
| **C004** | 还款释额 | **还本金时触发**（含前期、催收、减免，只要应还本金减少就算） | 锁定额度 -= 本次还本金 | ⚠️ 文档说**每次还本金都触发**，但770.4案例中只在末期触发 → **2-3月bug** |
| **C008** | 用信失败释额 | 用信审核不通过 / 放款失败 | 锁定额度 -= 本次用信额度 | 与还款无关，是用信失败的回滚 |
| **C010** | 用信确认临时额度调额 | 用户用信时选择使用临额 | 只更新临时额度，**不更新主额** | 在线临额发放 |
| **C013** | 离线刷临时额度 | 技术侧手动触发/后台上传数据 | 只更新临时额度 | 离线临额发放 |
| **C014** | 离线刷主额度 | 技术侧手动触发/后台上传数据 | 更新主额&临时额度 | 离线主额调整 |
| C001 | 新客授信 | 新客提交进件 | 首贷决策流输出全局额度 | — |
| C002 | 单期还清调额 | 客户还清单期时触发（2025-08-27改为每期） | 复贷进件决策流 | 事件执行顺序：C004先于C002 |
| C007 | 老客再授信 | 额度失效的老客再次进件 | 复贷进件决策流 | — |
| C009 | 老客额度变更 | 额度未失效的老客再次进件 | 复贷进件决策流 | — |
| C005 | 营销系统触发转产决策流 | 授信成功超24h未用信 / 结清超24h未进件 | 营销任务触发 | — |
| C011 | 用信预指弹留弹窗 | — | — | — |
| C012 | 支付后转产 | — | — | — |

### 🔍 C004 vs C008 关键差异（必须区分！）

| 维度 | C004 还款释额 | C008 用信失败释额 |
|------|--------------|-----------------|
| 触发场景 | 还本金（每期、催收、减免） | 用信审核不通过 / 放款失败 |
| 释放金额 | 本次还本金金额 | 本次冻结的用信额度 |
| 发生频率 | 高（每次还款） | 低（用信失败是少数） |
| 与770.4的关系 | ⚠️ **核心bug点**：应每次还都释额，实际只在末期释额 | 无关 |

### 🎯 对之前"解冻只在末期触发"结论的修正

**之前的结论**（基于数据观察）：
> 解冻只在末期还款同一秒触发，且只释放末期本金 → 残留=非末期本金

**文档设计意图**（V1.5）：
> C004应在**每次还本金**时触发，释放对应的本金金额

**实际数据与文档的矛盾**：
- 770.4案例中，两笔3月老贷的**前期还款没有触发C004释额**
- 只有末期还款时触发了C004，且只释放了末期本金
- 这说明**仅3月临额存在实现bug**：C004只在末期触发，而非每期触发
- **4月起此bug已修复**（4月及以后各月残留≤14比索，精度误差级）
- **主额无此bug**：各月主额已结清残留均为精度误差级（几百~几千比索）

### 🏦 主额 vs 临额 残留对比（全量已结清残留，排除在贷）

| 维度 | 主额(MAIN) | 临额(TEMP) |
|------|-----------|-----------|
| 冻结事件 | C003 用信冻结 | C003 用信冻结（先主后临） |
| 解冻事件 | C004 还款释额 | C004 还款释额 |
| 3月已结清残留 | 332笔/169比索 | **111笔/40,120比索**（bug） |
| 4~10月已结清残留 | 各月几十~几百笔/几百~几千比索 | 各月个位数/≤14比索 |
| 是否有bug | **无** | **仅3月有，4月起修复** |

## �� 关键公式与恒等式

### 恒等式1：合同额拆分（逐笔100%成立）
```sql
contract_amount = risk_credit_limit(MAIN FREEZE) + temp_grant_amount(TEMP used)
```

### 恒等式2：本次实到账临额（98.7%命中）
```sql
实际TEMP FREEZE_LIMIT冻结额 = C010.change_total_grantamount - C010.change_used_grantamount
```
⚠️ 注意：`change_used_grantamount`是**发放前存量占用**，不是"本次支用"！

### 账户级恒等式：存量占用（动态）
```sql
change_used_grantamount(t) = Σ_{TEMP事件 ≤ t, 同limit_main_id}(FREEZE_LIMIT − UNFREEZE_LIMIT)
```

### 结清后残留公式（无单一闭式，只能台账还原）
```sql
残留 = 临时冻结额 − 实际解冻额
实际解冻额 ≈ N × 末期本金（N因笔而异，无固定公式）
```

## ⚠️ Presto 陷阱清单

1. **camera_id类型不统一**：`s02_loan_repayment.camera_id`是decimal，`s02_loan.camera_id`是bigint。关联统一用`cast(camera_id as bigint)`
2. **used_detail无change_desc**：查这个字段会直接报错
3. **临额查询必须加limit_type='TEMP'**：否则主额/临额串值
4. **2025-12-09起所有额度表查主额需加limit_type='MAIN'**
5. **GROUP BY不能用别名**：必须子查询包装
6. **yj.temp_grant_amount是bigint分**：除以1000.0才是比索
7. **C010的change_desc固定值**："用户点确认借款页面创建临额"——不是每次实际使用
8. **单页1000行上限**：SQL侧无需关心，Python封装已处理

## 🧪 核心判定逻辑（已修正过，不要重复踩坑）

### "已结清"判定 ✅ 正确写法
```sql
max(case when state <> 1 then 1 else 0 end) = 0
-- 所有期state=1才算结清。不要用min（会有一期已还就判结清）
```

### "排除当日解冻延迟" ✅ 正确写法
```sql
date_diff('day', max(fact_time), timestamp'2026-10-14 00:00:00') >= 7
-- 账龄≥7天才是稳态，否则当日解冻延迟会假阳性
```

### "解冻事件码" ✅ 正确判定
```sql
change_action = 'UNFREEZE_LIMIT'
-- 不要只看事件码C004/C008（C008约4%也能命中UNFREEZE_LIMIT）
```
