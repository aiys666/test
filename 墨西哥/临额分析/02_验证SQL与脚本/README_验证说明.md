# 存量占用/结清后残留机制 —— 验证说明

## 📖 背景

2026-10-01 发现案例用户 `mid=1040160040722566` 每次领取在线临额时，额度变更记录中的 `change_used_grantamount` 字段**恒为 770.4 比索**，不随发放额变化。本验证链条以此为锚点，逐步推理出：

> **770.4 来源于两笔 3 月老贷的临额 C004 解冻缺陷残留**——两笔贷款（biz 1620000395926822、1620000396309679）均在 2026-03-26 全额结清（每期 state=1，fact_capital=should_capital），但 **临额的 C004(还款释额) 只在末期还款时触发**，前期已还本金对应的临额冻结挂在账户上未释放。
>
> ⚠️ **与产品文档的矛盾**：《墨西哥循环额度》V1.5 明确规定 C004 应在**每次还本金**时触发（含前期、催收、减免），释放对应的本金金额。但实际数据中：
> - **临额(TEMP)**：仅 3 月放款的合同存在此 bug，4 月起已修复
> - **主额(MAIN)**：无此 bug，各月 C004 均正常每期触发
>
> **全量影响**：3 月临额已结清残留 111 笔 / 40,120 比索；4 月起各月残留 ≤14 比索（精度误差）。

## 🧮 3 条硬恒等式（数学证明）

### 恒等式 1：合同额拆分（逐笔 100% 成立）

```sql
contract_amount = risk_credit_limit(MAIN FREEZE) + temp_grant_amount(TEMP used)
```

| 项目 | 说明 |
|------|------|
| 验证位置 | SQL 4-1（案例用户）、SQL 4-2（全窗口） |
| 关联键 | `cast(biz_id as bigint)` 关联 used_detail |
| 预期命中率 | **100%**（允许1比索舍入误差） |
| 业务含义 | 每笔放款的合同额 = 主额冻结 + 实际使用的临额，这是资金来源的恒等式 |

### 恒等式 2：本次实到账临额（98.7% 命中）

```sql
实际TEMP FREEZE_LIMIT冻结额
= C010.change_total_grantamount − C010.change_used_grantamount
```

| 项目 | 说明 |
|------|------|
| 验证位置 | SQL 4-3（全量）、SQL 4-4（分层）、SQL 4-5（失配样例） |
| 关联键 | `cast(external_id as bigint) = used_detail.biz_id` |
| 关键修正 | ~~旧结论：change_used_grantamount≈0不可用~~ → **作废！** 正确含义是"发放前存量占用" |
| 预期命中率 | **98.7%**（失配主要来自台账窗口截断） |
| 业务含义 | 这次用户实际能用到多少临额 = 名义发放 - 之前挂着的没解冻的 |

### 恒等式 3：账户级存量占用（动态公式）

```sql
change_used_grantamount(t)
= Σ_{TEMP事件 create_time ≤ t}(FREEZE_LIMIT − UNFREEZE_LIMIT)  -- 同limit_main_id
```

| 项目 | 说明 |
|------|------|
| 验证位置 | SQL 5-1 ~ 5-6（残留公式穷举） |
| 业务含义 | 每次发临额时系统自动算好的"你还有多少老临额没释放"，就是这个Σ累加 |
| 关键发现 | 这个公式导致770.4"传染"——每发一次C010都要扣掉770.4 |

## ⚠️ 口径陷阱清单（已踩过的坑，不要重复！）

### 陷阱 1：camera_id 类型不统一
```sql
-- ❌ 错误：直接关联
WHERE camera_id = 1620000395926822
-- ✅ 正确：cast后关联
WHERE cast(camera_id as bigint) = 1620000395926822
```
- `s02_loan_repayment.camera_id` 是 **decimal(38,6)**
- `s02_loan.camera_id` 是 **bigint**
- `used_detail.biz_id` 是 **bigint**

### 陷阱 2：used_detail 无 change_desc 字段
```sql
-- ❌ 错误：查不存在的字段
SELECT *, change_desc FROM ods.s05_user_creditlimit_used_detail
-- ✅ 正确：去掉
SELECT * FROM ods.s05_user_creditlimit_used_detail
```

### 陷阱 3：临额查询必须加 limit_type='TEMP'
```sql
-- ❌ 错误：主额/临额串值
SELECT * FROM ods_view_presto.s05_user_creditlimit_change_record WHERE change_event_type='C010'
-- ✅ 正确：加过滤
SELECT * FROM ods_view_presto.s05_user_creditlimit_change_record WHERE limit_type='TEMP' AND change_event_type='C010'
```

### 陷阱 4："已结清"判定逻辑反转
```sql
-- ❌ 错误：min搞反了（有一期已还就判"已结清"）
min(case when state<>1 then 1 else 0 end) = 0  -- min=0是对的，但容易搞反
-- ✅ 正确：max更直观（只要有一期未还max就是1）
max(case when state<>1 then 1 else 0 end) = 0  -- max=0 才是全部结清
```

### 陷阱 5：yj.temp_grant_amount 是 bigint 分
```sql
-- ❌ 错误：直接当比索用
sum(temp_grant_amount) AS used_amt  -- 单位是分！
-- ✅ 正确：除以1000得比索
sum(temp_grant_amount / 1000.0) AS used_amt  -- 单位是比索
```

### 陷阱 6：change_used_grantamount 不是"本次支用"
```sql
-- ❌ 旧错误结论（已作废）：
--   "change_used_grantamount ≈ 0，这个字段不可用"
-- ✅ 正确含义：
--   change_used_grantamount = 发放前已有的存量占用（抵扣额）
--   本次实际能用 = change_total_grantamount - change_used_grantamount
```

### 陷阱 7：台账窗口截断导致假阳性
```sql
-- ❌ 错误：窗口截在 10-08 00:00，切掉了 10-08 还款对应的解冻
create_time < timestamp'2026-10-08 00:00:00'
-- ✅ 正确：窗口放宽到 10-15，再用账龄过滤当日延迟
create_time < timestamp'2026-10-15 00:00:00'
-- 稳态异常集：额外加 date_diff('day', last_pay_t, timestamp'2026-10-14 00:00:00') >= 7
```

### 陷阱 8：C004 和 C008 虽然都是 UNFREEZE_LIMIT，但语义完全不同！
```sql
-- ⚠️ 关键区分（来自《墨西哥循环额度》V1.5）:
-- C004 = 还款释额: 还本金时触发(含前期/催收/减免), 锁定额度 -= 本次还本金
-- C008 = 用信失败释额: 用信审核不通过/放款失败, 锁定额度 -= 本次用信额度

-- 统计解冻总量时: 按动作判定（覆盖C004+C008）
change_action = 'UNFREEZE_LIMIT'  -- ✅ 正确

-- 分析770.4机制时: 必须区分！只看C004(还款释额)
change_event_type = 'C004'  -- ✅ 正确(只看还款解冻)

-- ❌ 错误: 把C008当作"还款解冻"来判断冲突
--   C008是用信失败的回滚，与还款无关，不应算作"还款解冻"
```

## 🔧 业务影响评估

### 展示口径 vs 评估口径

| 维度 | 展示口径（用户看到的） | 评估口径（实际到账的） |
|------|----------------------|----------------------|
| 名义发放 | change_total_grantamount | — |
| 实际到账 | — | change_total_grantamount - change_used_grantamount |
| 被抵扣 | — | change_used_grantamount（存量残留） |

### 残留客群特征
- **集中时间段**：仅 2026-03（3月放款的临额合同）
- **影响范围**：仅临额(TEMP)，主额(MAIN)无此bug
- **客群画像**：2/3/4期贷均有，C004只在末期触发（平均解冻次数远小于期数）
- **当前状态**：4月起已修复，各月残留≤14比索（精度误差）
- **bug根因**：产品文档规定C004每次还本金都触发，但3月临额实际只在末期触发

### 影响量级（全量已结清残留，排除在贷）
| 指标 | 数值 | 说明 |
|------|------|------|
| 3月临额已结清残留 | 111笔 / 40,120比索 | bug影响面 |
| 4~10月临额已结清残留 | 各月个位数 / ≤14比索 | 精度误差，已修复 |
| 主额已结清残留 | 各月几十~几百笔 / 几百~几千比索 | 精度误差，无bug |
| 案例用户770.4 | 2笔3月合同（498+272.4） | 临额前期未解冻 |
