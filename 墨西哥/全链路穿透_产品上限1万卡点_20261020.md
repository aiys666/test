> 目标 mid：1040160059697504（Tuna Cash / yawey，产品 D_1_03）

> 原始底数：`墨西哥/_fw_data/chain_mid1040160059697504_raw.csv`（36 条节点全字段）

## 一、结论速览

核心发现：**「1万」有两个，来源不同、卡的东西不同**，用户最终能借多少由它们叠加决定。

| # | 约束 | 量 | 落在哪里 | 卡什么 |
|---|---|---|---|---|
| ① | 主额可用（授信剩余） | `min(主额可用, daily_max)` | `ods_view_presto.s05_user_credit_limit`(MAIN) | — |
| ② | **用户级「单日最大可借」** | `daily_max_available_limit` | 节点 **1077** `fd_single_grantcredit_amount_cap`；`s05_user_credit_limit`(MAIN) | **「主额 + 离线临额」同池封顶**（本例 7000；多数用户 10000） |
| ③ | 今日总可用额度 = ① + 剩余离线临额 | `total_available_limit` | 离线临额节点 **1514**；`mx.yuhan_temp_limit_base_table_his_20260924` | 运营话术用口径，**不代表页面可借** |
| ④ | **产品级「上限」** | `ods.s03_product.limit_max` | `ods.s03_product`（pid=6120001545073325 = E_07_04_31_35X2_20_10） | **页面展示 / 单笔合同上限**（常态 10000 → 本次测试 15000） |
| ⑤ | 在线临额（**池外叠加**） | `C010发放 − C010已占用` | `s05_user_creditlimit_change_record`(TEMP, C010) | **唯一能突破 1万 的通道** |

**用户最终能借 ≈ ① + ⑤**；**页面看到 ≈ min(③, ④)**。

- **纯主额池（主额 + 离线临额）受 ② 封顶，合同永远 ≤ 1万** —— 本轮 10 月 47 笔 >1万 合同**全部**带在线临额，**0 笔例外**（见第五节）。
- **在线临额（⑤）在池外叠加**：复贷合同事实上限 = 10000 × (1+type1 比例 60%) = **16000**，样本最大值恰为 16000。
- **离线临额（C015）与主额同池，不额外变现**：用户持有 10500 离线临额，合同仍卡在 10000。

对目标 mid 1040160059697504：① = min(22550, 7000) = 7000，③ = 7000 + 离线临额 6750 = **13750**；④ = 10000（常态）→ 页面显示 **10000**；④ = 15000（本次测试）→ 页面显示 **13750**。

> 关键：**④ 卡片发生在产品配置层，不在风控决策流节点里** —— 风控侧全链路 36 个节点没有任何一个输出 10000/15000，只输出 ③ 与各分项；② 是用户级封顶（节点 1077），与产品级 ④ 是**两个不同的量**，当前两者恰好都是 1万，容易混淆。

## 六、待产品侧确认（风控侧无法定论）

数据已能定论的部分（无需产品侧确认）：
- ✅ 「纯主额」合同上限 = 1万（47 笔 >1万 全部带在线临额，0 例外）；
- ✅ 离线临额与主额**同池**，不额外变现（5.2 反例）；
- ✅ 在线临额在池外叠加，复贷事实上限 = 10,000×(1+60%) = 16,000（样本最大值 16,000）。

仍需产品/前端确认：
1. **前端「可借额度」取小实现**：确认页面展示是否严格为 `min(total_available_limit, s03_product.limit_max)`。风控决策流不承载该取小，全链 36 节点无 10000/15000 落值。
2. **② 与 ④ 的叠乘关系**：`daily_max_available_limit`（节点 1077，用户级）与 `s03_product.limit_max`（产品级）当前恰好都是 1万，需确认两者是「同值巧合」还是「同一个配置点写两处」——这决定改 1万5 时**是否要同时改 1077 的用户级上限**。
3. **15000 未在风控侧出现**：近 3 天（10-17~10-20）节点 1077 全量 cap 分布为 400~10000，**无 15000**，说明 1万5 测试只改了产品配置、**未同步进 1077**。若 ② 也参与封顶，则该测试对「主额+离线」池可能**无效**，需确认。

## 七、复现 SQL

```sql
-- 1) 离线临额决策流 ③ 与分项（及公式回算）
select cast(mid as bigint) mid, data_date, load_time, temp_limit_tag,
       curr_main_available_limit, daily_max_available_limit,
       temp_limit_issue_amount, curr_temp_used_credit_limit, total_available_limit
from mx.yuhan_temp_limit_base_table_his_20260924
where cast(mid as bigint) = 1040160059697504
order by load_time;

-- 2) 全链路节点穿透
select id, createtime, mid, biz_id, modelmainid, modeltype, strategytype, productid, inputdata, outputdata
from ods.s21_risk_model_record
where cast(mid as varchar) = '1040160059697504'
  and createtime >= timestamp'2026-10-13 00:00:00' and createtime < timestamp'2026-10-16 00:00:00'
order by createtime, id;

-- 3) 产品上限 ④
select pid, product_name, min_amount, max_amount, limit_min, limit_max, limit_interval,
       create_date, update_date, update_user
from ods.s03_product
where cast(pid as varchar) in ('6120001545073325','6120001545037199','6120001544986006');

-- 4) 用户级每日可借上限（= 节点1077 的 cap）
select * from ods_view_presto.s05_user_credit_limit
where cast(mid as varchar) = '1040160059697504';

-- 5) 【判据一】合同>1万 的笔里，有没有不带临额的？（应为 0）
select count(*) total_gt_1w,
       sum(case when coalesce(temp_grant_amount,0)=0 then 1 else 0 end) as temp_zero,
       sum(case when coalesce(temp_grant_amount,0)>0 then 1 else 0 end) as temp_gt0
from mx.report_application_funnel7_table
where issue_date >= date'2026-10-01' and issue_date <= date'2026-10-19'
  and if_issue = 1 and contract_amount > 10050;

-- 6) 【判据二】合同>1万 的逐笔明细（主额分量 = 合同 − 临额/1000，应≤10000）
select mid, issue_date, cast(product_level as varchar) plevel, apply_amount, contract_amount,
       temp_grant_amount, contract_amount - coalesce(temp_grant_amount,0)/1000.0 as main_component,
       credit_amount, daily_max_available_limit
from mx.report_application_funnel7_table
where issue_date >= date'2026-10-01' and issue_date <= date'2026-10-19'
  and if_issue = 1 and contract_amount > 10050
order by contract_amount desc;

-- 7) 【判据二】样本 mid 的临额变更事件（C003 主额冻结 / C010 在线临额）
select cast(mid as varchar) mid, create_time, change_event_type, limit_type,
       change_total_grantamount, change_used_grantamount
from ods_view_presto.s05_user_creditlimit_change_record
where cast(mid as varchar) in ('1040160069449344','1040160068112910','1040160069400979','1040160051069987')
  and create_time >= timestamp'2026-10-01 00:00:00' and create_time < timestamp'2026-10-20 00:00:00'
order by mid, create_time;

-- 8) 【判据四】92.4 表最新批次 今日总可用额度 分桶（注意 data_date 为 varchar 'yyyymmdd'）
select case when total_available_limit > 20000 then '>20000'
            when total_available_limit > 15000 then '15000~20000'
            when total_available_limit > 10000 then '10000~15000'
            when total_available_limit = 10000 then '=10000'
            else '<=10000' end bucket,
       count(*) rows_cnt, count(distinct mid) mids
from (
  select cast(mid as bigint) mid, total_available_limit,
         row_number() over(partition by cast(mid as bigint) order by load_time desc) rn
  from mx.yuhan_temp_limit_base_table_his_20260924
  where data_date >= '20261001'
) x where rn = 1
group by 1 order by 1;
```

> 注：`mx.yuhan_temp_limit_base_table_his_20260924.data_date` 是 `varchar` 型 `yyyymmdd`（如 `'20261015'`），不能与 `date` 直接比较。
