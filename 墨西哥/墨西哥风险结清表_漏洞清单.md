## 三、漏洞详情

### 🔴 漏洞1: settle_time取首贷app_time而非结清时间

**位置**: L837

**问题代码**:
```sql
min(case when b1.is_reloan = 'new' then b1.app_time else null end) 
  over (partition by b1.mid) as settle_time
```

**影响**:
- `settle_time`本应是**结清时间**,但这里取的是首贷用户的`app_time`(进件时间)
- 后续所有`date_diff('day', settle_time, app_time)`恒等于0(因为settle_time就是某个app_time)
- 导致所有时间窗口(7/14/21...180天)的筛选条件失效,**所有进件都被计入所有窗口**
- 逾期率、放款金额、转化率等所有指标的时间窗口统计全部错误

**修复**: 应从`darren_jieqing_dt_base_table`取真正的`settle_time`

---

### 🔴 漏洞2: t_fact_amt_tot双重时间限制,且第一个条件恒为0

**位置**: L816-831

**问题代码**:
```sql
sum(case when date_diff('day', settle_time, app_time) <= 7 
         and date_diff('day', settle_time, fact_time) <= 7 
    then fact_capital+fact_interest end) as t7_fact_amt_tot
```

**影响**:
- 第一个条件`date_diff(settle_time, app_time) <= 7`:因漏洞1的settle_time=min(app_time),此条件对首贷进件恒为0天≤7(恒真),对复贷进件可能>7(被过滤)
- 第二个条件`date_diff(settle_time, fact_time) <= 7`:限制了还款必须在首贷进件后7天内
- 两个条件叠加,**实际统计的是"首贷进件后7天内的还款"**,而非"结清后7天窗口内的还款"
- 与外层`old_customer_loan_*_7d`的口径不一致

**修复**: `settle_time`改用真实结清时间后,条件应为`date_diff('day', settle_time, fact_time) <= 7`(去掉第一个条件)

---

### 🔴 漏洞3: 首次结清筛选条件`settle_time >= '2026-08-14'`会漏掉历史首次结清用户

**位置**: L492

**问题代码**:
```sql
where date(settle_time) >= date '2026-08-14'
```

**影响**:
- 这个条件限制了**结清时间≥8月14日**
- 但表名是`shouci_jieqing`(首次结清),如果用户首次结清在8月14日之前,会被漏掉
- `row_number() over (partition by jq_mid order by settle_time) as rn`取rn=1本意是取每个用户的**首次结清**,但加上日期过滤后,实际取的是"8月14日之后的首次结清"
- **8月14日前已结清的用户全部丢失**,样本量严重不足

**修复**: 应先取rn=1(全量首次结清),再按需过滤分析日期范围

---

### 🔴 漏洞4: 结清次数统计t12用mid关联,t13用identity关联,口径不一致

**位置**: L370-411

**问题代码**:
```sql
-- t12: mid维度
left join (select customer_id,fact_time,rid,state from s02_loan_repayment) t1
on cast(t0.jq_mid as bigint) = cast(t1.customer_id as bigint)

-- t13: identity维度
left join (...) t1
on t0.identity = t1.identity
```

**影响**:
- `repayment_clearing_count_index`(mid维度):只统计同一mid的结清次数
- `repayment_clearing_count_index_all`(identity维度):统计同一identity(可能多mid)的结清次数
- 如果用户有多个mid(换设备/换账号),t12会少算,t13会多算
- 两个指标用于AB测试分组的`settle_adjust_quota_cnt`判断,**口径不一致会导致分组偏差**

**修复**: 统一用identity维度,或明确两个指标的用途

### 🟡 漏洞6: `equal_houshou_should_interest`计算逻辑存疑

**位置**: L803

**问题代码**:
```sql
sum(interest + contract_amount - amount) as equal_houshou_should_interest
```

**影响**:
- 字段名"等额后收应还利息",但计算 = 利息 + 合同金额 - 实际放款 = 利息 + 砍头息
- 这实际是"总应还金额",而非"利息"
- 后续`old_customer_post_interest_rate = (equal_houshou_should_interest - contract_amount + real_issue_amount) / contract_amount`,化简后 = (interest + amount - amount) / contract_amount = interest / contract_amount
- **命名与实际计算不符**,增加维护难度

---

### 🟡 漏洞7: darren_jieqing_dt_table关联条件`is_settle_adjust_quota_flag=1`过滤大量数据

**位置**: L461

**问题代码**:
```sql
left join (...) t1 
on t0.jq_mid = t1.mid
and t0.settle_time < t1.create_time
and date_diff('day',date(t0.settle_time),date(t1.create_time)) < 5 
and is_settle_adjust_quota_flag = 1   -- ← LEFT JOIN的ON条件
```

**影响**: `is_settle_adjust_quota_flag=1`放在LEFT JOIN的ON条件中,而非WHERE中。这导致主表所有数据保留,但只有flag=1的才关联上t1。如果flag=0,t1字段全为NULL,后续依赖t1字段的计算会出错。

---

### 🟡 漏洞8: shouci_jieqing_dt_table关联条件`date(settle_time) >= '2026-05-25'`重复过滤

**位置**: L492, L533

**问题代码**:
```sql
-- L492 (子查询)
where date(settle_time) >= date '2026-08-14'

-- L533 (外层WHERE)
where date(settle_time) >= date'2026-05-25'
```

**影响**: 子查询已过滤`settle_time >= '2026-08-14'`,外层又过滤`>= '2026-05-25'`。两个日期不一致(8月14日 vs 5月25日),外层条件被内层条件覆盖,**5月25日-8月14日的数据仍被漏掉**。

---

### 🟢 漏洞9: 多处LEFT JOIN用rn=1去重,未处理NULL

**位置**: L344, L353, L366, L420, L433

**问题代码**:
```sql
left join (...) t7 on t0.jq_mid = t7.mid_t2 and t7.rn = 1
```

**影响**: 如果关联不到,rn为NULL,`rn=1`为false,但因为是LEFT JOIN的ON条件,主表数据仍保留。但t7字段为NULL,后续计算可能出错。

---

### 🟢 漏洞10: wxs_application_funnel子查询用group by去重,但字段不全

**位置**: L318-330

**问题代码**:
```sql
select mid, jq_phone, jq_app_group_sha256, jq_credit_no
from (
  select mid, phone as jq_phone, app_group_sha256, credit_no as jq_credit_no,
    row_number() over (partition by mid order by create_time desc) as rn 
  from mx.wxs_application_funnel) t0 
where rn = 1 
group by 1,2,3,4
```

**影响**: `row_number() over (partition by mid order by create_time desc)`取最新一条,但如果同一mid在不同app_group下有不同credit_no,只保留最新的一条,**可能丢失历史app_group信息**。
