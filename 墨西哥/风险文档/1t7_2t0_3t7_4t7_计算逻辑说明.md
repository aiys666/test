# 1t7 / 2t0 / 3t7 / 4t7 计算逻辑说明

> 对应 SQL：[01墨西哥风险宽表新口径.sql](./01墨西哥风险宽表新口径.sql)

## 一、命名规则

指标名格式为 **`{期数}t{N天}`**：第 `期数` 期还款，从它的应还日（`should_date`）起算，**超过 N 天** 时的表现标志。

| 指标 | 含义 |
|---|---|
| `1t7` | 第 1 期，应还日已过 7 天 |
| `2t0` | 第 2 期，应还日已过 0 天 |
| `3t7` | 第 3 期，应还日已过 7 天 |
| `4t7` | 第 4 期，应还日已过 7 天 |

## 二、计算口径

窗口 flag 定义在 `mx.wxs_vintage_all3`，核心是：

```sql
due0_flag = if(date_diff('day', r.should_date, current_date) > 0,  1, 0)
due7_flag = if(date_diff('day', r.should_date, current_date) > 7,  1, 0)
```

注意是 **`> N`（严格大于）**，不是 `>=`：

- `t0`：应还日之后 **第 1 天** 起才置 1；
- `t7`：应还日之后 **第 8 天** 起才置 1。

下游在 `mx.wxs_vintage_all4` 中把每一期横向展开，例如：

```sql
sum(if(indexs=1, due7_cnt, 0)) should_cnt_1_7   -- 1t7
sum(if(indexs=2, due0_cnt, 0)) should_cnt_2_0   -- 2t0
sum(if(indexs=3, due7_cnt, 0)) should_cnt_3_7   -- 3t7
sum(if(indexs=4, due7_cnt, 0)) should_cnt_4_7   -- 4t7
```

最后在 `mx.wxs_vintage_all5` 中重命名为 `is_t7_window_1 / is_t0_window_2 / is_t7_window_3 / is_t7_window_4`。

其中：

- `should_cnt_{期数}_{N}`：应还数（分母）
- `overdue_cnt_{期数}_{N}`：逾期数（分子）
- 逾期率 = `overdue_cnt / should_cnt`

## 三、时间轴示例（2 × 7 期产品，共 14 天）

假设 0901 放款、每期 7 天、共 2 期（合计 14 天），则：

| 期数 | 应还日 | 1t0 | 1t7 | 2t0 | 2t7 |
|---|---|---|---|---|---|
| 第 1 期 | 09/08 | 09/09 起 =1 | 09/16 起 =1 | — | — |
| 第 2 期 | 09/15 | — | — | 09/16 起 =1 | 09/23 起 =1 |

回答两个关键问题：

1. **“0901 放款、到期后，会立马有 2t0 和 1t7 吗？”**

   - `1t0`：会。第 1 期 09/08 到期，09/09 就置 1。
   - `1t7`：**不会立马有**。要等到 09/08 之后第 8 天（09/16）才置 1。
   - `2t0`：**不会立马有**。第 2 期 09/15 才到期，09/16 才置 1。

   即“到期那一刻”真正立刻能看到的只有 `1t0`；`1t7` 和 `2t0` 都还要再等。

2. **“3t7 / 4t7 什么时候有数据？”**

   2 期产品的真实期数 `loan_indexs = 2`，本来没有第 3、4 期。数据来自 `mx.wxs_vintage_all2` 的复制补齐逻辑：

   ```sql
   union all
   select camera_id, 3 indexs, should_date, fact_date, state from mx.wxs_vintage_all1 where loan_indexs < 3
   union all
   select camera_id, 4 indexs, should_date, fact_date, state from mx.wxs_vintage_all1 where loan_indexs < 4
   ```

   而 `mx.wxs_vintage_all1` 只保留每笔贷款的**最后一期**（`lr.indexs = loan_indexs`）。因此这笔 2 期贷款：

   - “第 3 期”“第 4 期”的 `should_date` 都被复制成 **第 2 期（最后一期）的应还日 09/15**，并非真实存在。
   - 所以：
     - `3t7` = 09/15 + 7 天 → **09/23 起才有值（=1）**
     - `4t7` = 09/15 + 7 天 → **同样 09/23 起才有值（=1）**

   结论：**3t7 与 4t7 的时间点完全一致，都跟随“最后一期”的到期日走**，因为第 3/4 期不存在，只是把最后一期“顶”到了那个位置。

## 四、为什么这么设计

1. **统一宽表列结构**：不同贷款期数（2/3/4 期…）都要在同一张表横向铺开 `indexs=1..4`（甚至到 10 期）的指标列。不补齐的话，2 期产品的 `3t7/4t7` 列就是空的，下游报表列不齐、聚合口径会乱。

2. **悲观逾期口径**：把“最后一期之后的位置”继续用“最后一期是否在逾期”填满，等于持续跟踪“这笔贷款期满之后到底还清没有”。对短期限产品，`4t7` 实际衡量的是“最后一期到期后 7 天还在不在逾期”，是最坏情况（悲观）的坏账口径。

3. **Vintage 账龄分析统一**：每个 `{期数}t{N}` 都是“该期应还日 + N 天”的固定窗口，便于按放款月做 cohort 分析，不因产品期数差异而缺列。

## 五、注意事项（疑似 Bug）

在 `mx.wxs_vintage_all4` 的 3t7 这一行：

```sql
, sum(if(indexs=3, due3_cnt, 0)) should_cnt_3_7   -- 分子用了 due3_cnt，疑似应为 due7_cnt
, sum(if(indexs=3, ovd7_cnt, 0)) overdue_cnt_3_7
```

对比 `1t7 / 2t7 / 4t7` 的应还数分子都是 `due7_cnt`，唯独 **3t7 的应还数分子写成了 `due3_cnt`**，会导致 3t7 的逾期率分母用错窗口、数值失真。建议将 `due3_cnt` 改为 `due7_cnt`。
