## 三、漏洞详情

### 🔴 漏洞1: indexs=3的7天字段用了3天的值(复制粘贴Bug)

**位置**: L786-789

**问题代码**:
```sql
, sum(if(indexs=3, due3_cnt, 0))    should_cnt_3_7      -- BUG: 应为 due7_cnt
, sum(if(indexs=3, ovd3_cnt, 0))    overdue_cnt_3_7     -- BUG: 应为 ovd7_cnt
, sum(if(indexs=3, due3_amount, 0)) should_capital_3_7  -- BUG: 应为 due7_amount
, sum(if(indexs=3, ovd3_amount, 0)) overdue_amount_3_7  -- BUG: 应为 ovd7_amount
```

**影响**: 第3期的7天应还/逾期笔数和金额,实际填的是3天的值。所有依赖`should_cnt_3_7`/`overdue_amount_3_7`的下游计算全部错误。

**修复**: 将`due3_*`/`ovd3_*`改为`due7_*`/`ovd7_*`

---

### 🔴 漏洞2: T0-T30逾期金额用了now_should_amt做比较

**位置**: L111-135

**问题代码**:
```sql
case 
    when t3.t0_fact_amt >= t2.now_should_amt then 0        -- BUG: 应为 t0_should_amt
    when t3.t0_fact_amt < t2.now_should_amt then t2.now_should_amt - t3.t0_fact_amt  -- BUG
    when t3.t0_fact_amt is null then t2.t0_should_amt
end as T0_OVERDUE_AMOUNT
```

**影响**: T0/T3/T7/T14/T30的逾期金额全部用`now_should_amt`(当前应还总额)做比较。当订单有多期未到期时,`now_should_amt > t0_should_amt`,导致**逾期金额虚高**。

**修复**: 所有`now_should_amt`改为对应的`tN_should_amt`

---

### 🔴 漏洞3: 还款明细跨期交叉Join,金额重复计算

**位置**: L687

**问题代码**:
```sql
left join ods_view_presto.s02_loan_repayment_detail rd on rd.camera_id = t1.id
-- 缺少 AND rd.indexs = t1.indexs 条件
```

**影响**: 同一笔还款明细被关联到该订单的所有期数。例如订单有2期,2026-01-05还款100元:
- 对第1期(应还01-01): date_diff=4天 → 计入t7窗口
- 对第2期(应还02-01): date_diff=-27天 → 计入tm3窗口

**同一笔还款被重复计入多个期数的不同窗口**,导致vintage回收金额虚高。

**修复**: 添加`AND rd.indexs = t1.indexs`

---

### 🔴 漏洞4: should_capital字段实际=本金+利息,命名混淆

**位置**: L685

**问题代码**:
```sql
select camera_id,
    sum(should_capital) + sum(should_interest) should_capital,  -- 实际=本金+利息,但命名为should_capital
    sum(should_capital) should_capit,                           -- 真正的本金
    sum(should_interest) should_interest
```

**影响**: 字段`should_capital`实际值是"本金+利息",但下游vintage_all31的`duem3_amount = if(duem3_flag=1, should_capital, 0)`把它当作纯本金使用。**逾期金额实际是"本金+利息"的逾期**,与字段语义不符。

**修复**: 重命名`should_capital`为`should_total`,下游改用`should_capit`

---

### 🟡 漏洞5: 逾期天数计算未扣除券(coupon_amount)

**位置**: L207

**问题代码**:
```sql
case when (should_capital + should_interest) = (fact_capital + fact_interest + subtract_capital + subtract_interest) 
          or state in (1,3,5) then 0
     else date_diff('day', date(should_time),current_date) end overdue_days
```

**影响**: 判断"是否还清"时未包含`coupon_amount`。有券订单即使已通过券抵扣还清,也不会被识别为"已还清",导致**逾期天数虚高**。

**修复**: `(fact + coupon_amount + subtract) = should` 才算还清

---

### 🟡 漏洞6: vintage_all4只透视indexs 1-4,丢失5-10期

**位置**: L700-818

**问题**: vintage_all2展开到了indexs 1-10,但vintage_all4的`sum(if(indexs=N, ...))`只写了N=1,2,3,4。**第5-10期的应还/逾期数据被完全丢弃**。

**影响**: 对多期产品(如分期),后期vintage分析数据缺失。

**修复**: 补充indexs 5-10的透视逻辑

---

### 🟡 漏洞7: if_issue用should_time而非release_time

**位置**: L1323

**问题代码**:
```sql
,CASE WHEN d.should_time IS NOT NULL THEN 1 ELSE 0 END AS if_issue  --是否放款
```

**影响**: `if_issue`基于还款计划的`should_time`判断,而非`c.release_time`(放款时间)。刚放款但尚未生成还款计划的订单会被判为`if_issue=0`,**漏统计放款量**。

**修复**: `CASE WHEN c.release_time IS NOT NULL AND c.state IN (1,2,3) THEN 1 ELSE 0 END`

---

### 🟡 漏洞8: wxs_risk_ttl未过滤s02_loan的state

**位置**: L142

**问题代码**:
```sql
from ods_view_presto.s02_loan t1   -- 未加 WHERE state IN (1,2,3)
```

**影响**: 主表包含state=0(待审核)/4(取消)/5(放款失败)/6(审核拒绝)/7(放款中)的订单,这些订单没有实际放款,但会被计入风险宽表,**可能虚增分母**。

**修复**: 添加`WHERE t1.state IN (1,2,3)`

---

### 🟢 漏洞9: 订单级聚合用max(should_time)丢失各期到期信息

**位置**: L169

**问题代码**:
```sql
select a.camera_id, sum(a.should_capital), sum(a.should_interest), max(a.should_time) should_time
```

**影响**: 订单有2期(1月到期+3月到期),聚合后should_time=3月(max值)。2月查询时`t0_should_num=0`,但1月那期实际已到期。**窗口标志位不准确**。(Vintage链all2-all5保留了各期明细,不受影响;risk_ttl链用于overdue_basetable,受影响)

**修复建议**: risk_ttl改为期级明细表,或改用min(should_time)

---

### 🟢 漏洞10: reloan_num的GROUP BY包含create_time

**位置**: L59

**问题代码**:
```sql
group by create_time, t1.id, t1.mid
```

**影响**: 如果同一用户在同一时刻有多个进件(create_time相同),会被合并为一行。外层`select distinct`后只保留一条,reloan_num可能与实际不符。

**修复建议**: 去掉create_time,改为`group by t1.id, t1.mid`
