## 三、漏洞详情

### 🔴 漏洞1: c表(授信等待节点时效)未去重,LEFT JOIN笛卡尔积膨胀

**位置**: L641-642

**问题代码**:
```sql
FROM ods_view_presto.s05_creditx_processor_record 
WHERE current_processor IN ('首贷授信等待节点','复贷授信等待节点')
```

**影响**: 
- c表查询同时取"首贷授信等待节点"和"复贷授信等待节点"
- 如果同一biz_id在两个节点都有记录,c表会产生**重复行**
- LEFT JOIN后主表a会**笛卡尔积膨胀**,下游统计笔数/金额全部虚高
- 与p15子查询(也取这两个节点)不同,p15用了`group by biz_id`去重,但c表没有

**修复**: c表加`GROUP BY biz_id`或用`row_number() over(partition by biz_id order by update_time desc)`取最新一条

---

### 🔴 漏洞2: 审批节点passed判断逻辑不一致,口径混乱

**位置**: L323-326 vs L386-393

**问题代码**:
```sql
-- p1(强反欺诈): 没有REFUSED就算通过
case when (sum(case when approve_result = 'REFUSED' then 1 end)) is null then 1 
    else 0 end as if_shou_anti_fraud_passed

-- p7(人审): 必须有PASSED才算通过
case when (sum(case when approve_result = 'PASSED' then 1 end)) >= 1 then 1 
    else 0 end as if_shou_normal_check_passed
```

**影响**:
- p1-p6(反欺诈/模型): 用"**无REFUSED则通过**"逻辑
- p7-p8(人审): 用"**有PASSED则通过**"逻辑
- 两种逻辑口径不一致:
  - 用户到了人审节点但还在pending(无PASSED也无REFUSED) → p7的passed=0,但p1的passed逻辑下=1
  - **漏斗转化率计算口径不统一**,节点间转化率不可比

**修复**: 统一为"无REFUSED则通过"或"有PASSED则通过",全表保持一致

---

### 🔴 漏洞3: s02_loan关联无state过滤,包含未放款订单

**位置**: L569-572

**问题代码**:
```sql
left join (select camera_id, release_time, contract_amount
from ods_view_presto.s02_loan) t6  -- 无 WHERE state IN (1,2,3)
```

**影响**: 
- s02_loan包含state=0(待审核)/4(取消)/5(放款失败)等未实际放款的订单
- 这些订单的`release_time`和`contract_amount`会被关联到宽表
- 下游用`release_time`计算放款时间、用`contract_amount`计算成交金额时**可能包含无效数据**

**修复**: 添加`WHERE state IN (1,2,3)`

---

### 🔴 漏洞4: should_capital/should_interest聚合无日期过滤,且全表扫描

**位置**: L591-595

**问题代码**:
```sql
left join(select camera_id,
  sum(cast(should_capital as double)) as should_capital,
  sum(cast(should_interest as double)) as should_interest
from ods_view_presto.s02_loan_repayment
group by camera_id) t10  -- 无日期过滤
```

**影响**: 
- **性能问题**: 全表扫描s02_loan_repayment(千万级),无日期过滤
- **数据问题**: sum了所有期的应还本金/利息,如果有多期,`should_capital`是所有期之和,而非当期
- 下游用`should_capital`和`should_interest`计算利率/坏账时口径不清

**修复**: 添加日期过滤`WHERE should_time >= date_add('day',-720,date(now()))`

---

### 🟡 漏洞5: 复贷人审规则passed判断用"myDecisionResult is null"

**位置**: L448

**问题代码**:
```sql
case when (sum(case when cast(json_extract(context_result, '$.myDecisionResult') as varchar) is null then 1 end)) >= 1 then 1 
    else 0 end as if_fu_normal_rule_check_passed
```

**影响**: 
- 复贷人审规则的"通过"判断是`myDecisionResult is null`
- 这意味着**没有决策结果就算通过**,逻辑很奇怪
- 如果是系统异常导致context_result为空,也会被判为"通过"
- 与首贷人审规则(L436,用`myDecisionResult = 'Normal'`)逻辑不一致

**修复**: 确认业务逻辑,如果null也算通过需加注释说明

---

### 🟡 漏洞6: double_loan的11个渠道硬编码,无注释

**位置**: L185-195

**问题代码**:
```sql
case when app_channel in ('cdf58da5-801a-4575-9af4-a56453cea6f3', 
    'cbcf1f5e-092a-44ad-abb9-7d5af8f023cb', ...共11个...) then 1 else double_loan end as double_loan
```

**影响**: 
- 这11个渠道被强制设为`double_loan=1`(复贷),但**没有注释说明原因**
- 如果新增渠道或渠道下线,需要手动维护这段硬编码
- 维护成本高,且容易遗漏

**修复**: 改为配置表关联,或加注释说明这11个渠道的业务含义

---

### 🟡 漏洞7: s02_loan关联用ceil(camera_id)转varchar

**位置**: L573

**问题代码**:
```sql
on t0.biz_id = cast(ceil(t6.camera_id) as varchar)
```

**影响**: 
- `ceil(camera_id)`取整再转varchar关联
- 如果camera_id是浮点数(如1620000455218220.5),ceil会变成1620000455218221,**丢失精度**
- 如果camera_id本身是整数,ceil无意义,多此一举
- 类型转换+数学函数组合,影响查询性能

**修复**: 直接`on t0.biz_id = cast(t6.camera_id as varchar)`,或用bigint关联

---

### 🟡 漏洞8: tmp_wenj_product_table只取昨天数据,与主表720天不匹配

**位置**: L16

**问题代码**:
```sql
where etl_date >= to_char(date_add('day', -1, current_date), 'yyyymmdd')  -- 只取昨天
```

**影响**: 
- f表(tmp_wenj_product_table)只取**昨天一天**的数据
- 但主表a取**近720天**的数据
- 如果biz_id不是昨天的(比如前天的进件),f表关联不到,`credit_amount`和`daily_max_available_limit`为NULL
- 下游依赖这两个字段的分析会**大量缺失**

**修复**: f表日期范围应与主表一致,或改为全量

---

### 🟢 漏洞9: e表首复贷标签只取productid 310,330,331,且etl_date固定2025年

**位置**: L650-652

**问题代码**:
```sql
where productid in (310,330,331)
and strategytype = 'CHAMPION'
and etl_date >= '20250101'  -- 硬编码2025年
```

**影响**: 如果首复贷判断的产品id变更,需要手动维护。etl_date固定2025年1月,2026年后的数据可能需要更新。

---

### 🟢 漏洞10: c表时效标记的update_time可能为NULL

**位置**: L607-608

**问题代码**:
```sql
CASE WHEN approve_result='PASSED' AND date_diff('minute',create_time,update_time)<=24 * 60 ...
```

**影响**: 如果授信等待节点还在pending(未update),`update_time`为NULL,`date_diff`会返回NULL,整个CASE为0。这在逻辑上可能正确(pending不算通过),但需确认。
