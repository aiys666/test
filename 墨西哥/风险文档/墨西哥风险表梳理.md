# 墨西哥风险相关表梳理

> 数据源：墨西哥 Presto（盘古4.0，data.tengoprestamos.com）
> 更新日期：2026-08-27
> 涉及表：s21_risk_strategy_record（策略记录）、s21_risk_model_record（模型记录）、s09_third_request_record_log（三方请求日志）、s09_os_data_config（数据源配置）

---

## 一、四张表总览：它们在一笔进件里扮演什么角色

一笔进件（biz_id）进来后，系统会经历：**三方数据调用 → 策略决策 → 模型打分** 三个环节，四张表分别记录这三个环节：

```
进件单 (biz_id / externalid)
    │
    ├─【调三方】s09_third_request_record_log ← 关联 s09_os_data_config（数据源是啥）
    │    记录每次调了哪个三方、返回了什么
    │
    ├─【跑策略】s21_risk_strategy_record
    │    记录命中哪个策略、决策结果(PASS/REJECT)
    │
    └─【跑模型】s21_risk_model_record
         记录策略里跑了哪些模型、模型分多少
```

**一句话**：`strategy_record` 看"决策结果"，`model_record` 看"模型分"，`third_request_record_log` 看"三方数据"，`os_data_config` 看"三方数据源是啥"。

## 二、表①：s21_risk_strategy_record（风险策略记录表）

### 作用
**每笔进件命中了哪个策略、什么版本、决策结果如何。**

### 关键字段

| 字段 | 类型 | 含义 | 使用要点 |
|------|------|------|---------|
| `id` | bigint | 主键 | |
| `createtime` | timestamp | 记录创建时间 | 近似策略执行时间 |
| `externalid` | varchar | **进件单号** | **= biz_id**，关联进件主表 |
| `executionid` | bigint | 执行批次id | 同一笔进件的一次完整风控执行共用一个 |
| `productid` | bigint | 产品id | 358/359等，区分产品线 |
| `eventid` | bigint | 事件id | 触发什么事件（如337申请、173=?, 194=?） |
| `channelid` | bigint | 渠道id | |
| `originstrategyid` / `downstreamstrategyid` | bigint | 上游/下游策略id | 策略流转链路 |
| `strategytype` | varchar | **策略类型** | `CHAMPION`=正式策略，`SHADOW`=影子策略（对比测试用） |
| `strategydefid` | bigint | 策略定义id | 策略版本id |
| `strategymainid` | bigint | **策略主id** | 同一策略不同版本共享主id |
| `inputdata` / `outputdata` | varchar | 策略输入/输出（JSON） | 能看到决策依据 |
| `decisionresult` | varchar | **决策结果** | `PASS`=通过，`REJECT`=拒绝 |
| `success` | varchar | 是否执行成功 | true/false |
| `mid` / `cust_id` / `biz_id` | bigint | 客户id/用户id/进件单号 | 关联键 |
| `etl_date` | varchar | ETL分区日期 | **查询必须带这个条件** |

### 实际数据样例
```
strategytype  decisionresult  success   cnt
CHAMPION      PASS            true     183857   ← 正式策略通过
SHADOW        PASS            true      60943   ← 影子策略通过（不生效，仅对比）
CHAMPION      REJECT          true       5576   ← 正式策略拒绝
SHADOW        REJECT          true        301
CHAMPION                     false        139   ← 执行失败
```

### 使用要点
- **`strategytype`：CHAMPION vs SHADOW** 是核心——CHAMPION 是真正生效的决策，SHADOW 是影子测试（并行跑但不影响结果），做分析时**默认只取 CHAMPION**
- **`etl_date`** 是分区字段，查询必须限定，否则全表扫描

## 三、表②：s21_risk_model_record（风险模型记录表）

### 作用
**策略里每个模型跑了什么、模型分多少、调用成本。**

### 关键字段

| 字段 | 类型 | 含义 | 使用要点 |
|------|------|------|---------|
| `id` | bigint | 主键 | |
| `createtime` | timestamp | 执行时间 | |
| `externalid` | varchar | **进件单号** |= biz_id |
| `executionid` | bigint | 执行批次id | 与 strategy_record 共用 |
| `strategytype` | varchar | 策略类型 | CHAMPION/SHADOW |
| `strategydefid` | bigint | 策略定义id | 关联 strategy_record |
| `modelid` | bigint | 模型定义id | 模型的版本 |
| `modelmainid` | bigint | **模型主id** | 同一模型不同版本共享 |
| `modeltype` | varchar | **模型类型** | `SCORECARD`=评分卡，`DECISIONTABLE`=决策表，`PMML`=机器学习模型 |
| `nodeserial` | bigint | 节点序号 | 策略里跑模型的顺序 |
| `inputdata` / `outputdata` | varchar | 模型输入/输出（JSON） | **outputdata 里是模型分** |
| `matchedrules` / `weightruleresult` | varchar | 命中规则/加权规则结果 | |
| `cost` | bigint | 调用成本 | 可能是耗时或费用 |
| `mid` / `cust_id` / `biz_id` | bigint | 客户/用户/进件单 | |
| `etl_date` | varchar | 分区日期 | 必须带 |

### 实际数据样例（outputdata = 模型分JSON）
```
modeltype      nodeserial  outputdata                                                        cost
SCORECARD      14          {"reject_rule_score_before_adjusted":-2.0}                         0
SCORECARD      15          {"reject_rule_score":-2.0}                                         1
DECISIONTABLE  16          {"sd_reject_level_V1":6}                                           3
SCORECARD      17          {"sd_duomodel_votegood_scorecard_low_20260305":0.0}                1
PMML           8           {"m690noapp_old_1t3_ad_1018_p1":0.5517,...}                       65
```

### 使用要点
- **一进件会跑多个模型**（nodeserial 从低到高），每个模型一行
- `outputdata` 是 JSON 字符串，**需要解析才能拿到模型分**
- `modeltype` 区分模型种类：SCORECARD 是传统的评分卡（输出规则分），PMML 是机器学习模型（输出概率分）
- `cost` 大的通常是 PMML（复杂模型调用成本高）

## 四、表③：s09_third_request_record_log（三方数据请求记录日志）

### 作用
**每次调三方数据源（征信、反欺诈、实名等）的记录，返回了什么。**

### 关键字段

| 字段 | 类型 | 含义 | 使用要点 |
|------|------|------|---------|
| `id` | bigint | 主键 | |
| `record_id` | bigint | 三方记录id | 关联三方平台自己的记录 |
| `mid` / `biz_id` | bigint | 客户/进件单 | 关联键 |
| `is_his` | integer | 是否历史重查 | 1=历史(老客户复查)，0=当前 |
| `create_time` | timestamp | 请求时间 | |
| `type` | integer | **数据源code** | **= os_data_config.code**，关联出数据源名称 |
| `resp_body` | varchar | **返回结果(JSON)** | 核心数据，需解析 |
| `external_id` | varchar | 外部请求id | |
| `etl_date` | varchar | 分区日期 | 必须带 |

### 实际数据样例（resp_body）
```
type   resp_body
401    {"message":{"20260126":2,"20260203":1,...}}          ← 某种黑名单/多头？
78     {"code":"SUCCESS","data":{"GD_X_32":249.79,...}}     ← advance 多平台（多头借贷特征）
1001   {"response_code":"00","result":{"mex_repayment_ability_f...}}  ← 还款能力评估
901    {"amlta_d60_daydiff_max":"41",...}                   ← 反欺诈特征
```

### 使用要点
- **type 关联 os_data_config.code** 才能知道调的是哪个数据源（见表④）
- `resp_body` 是核心，但**每个数据源的返回格式不同**，需要逐个解析
- `is_his` 区分当前申请 vs 历史复查，分析时注意口径

## 五、表④：s09_os_data_config（数据源配置表）

### 作用
**三方数据源的配置字典：数据源叫什么、请求/回调地址、code。**

### 关键字段

| 字段 | 类型 | 含义 | 使用要点 |
|------|------|------|---------|
| `id` | bigint | 主键 | |
| `name` | varchar | **数据源名称** | 如 mx_advance_curp（CURP实名）、yn_tongdun（同盾） |
| `type` | decimal | 类型 | 2=http接口，3=? |
| `os_indata_url` / `os_outdata_url` | varchar | 内部/外部数据源地址 | 能看到是哪个供应商 |
| `code` | bigint | **数据源code** | **= third_request_record_log.type** |
| `description` | varchar | 描述 | |
| `async` | bigint | 是否异步 | |
| `del_flag` | decimal | 删除标识 | 0=在用，1=删除 |

### 实际数据样例（code → 数据源）
```
id    name                            code  os_outdata_url
204   mx_advance_curp                 70    https://mex-api.advance.ai/...   ← Advance CURP实名
205   mx_liveness_detection           72    ...                               ← 活体检测
206   mx_advance_facecompar           71    ...                               ← 人脸比对
207   mx_advance_blacklist            77    ...                               ← Advance黑名单
208   mx_advance_multi_platform       78    ...                               ← Advance多平台（多头）
211   tanzhi_blackList                52    http://oversea.luckvay.cc/...     ← 探知黑名单

218   mx_nubarium_curp                120   https://curp.nubarium.com/...     ← Nubarium CURP
```

### 使用要点
- **把 `code` 映射到 `name`**，就能看懂 third_request 的 type 是什么数据源
- 常见供应商：Advance AI（advance_*）、探知（tanzhi_*）、同盾（tongdun）、Nubarium（nubarium_*）、FaceID/旷视（faceid）

## 六、四张表的关联逻辑（一张图）

```
                        进件单 biz_id
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
  三方请求日志          策略记录              模型记录
  s09_third_request   s21_risk_strategy    s21_risk_model
  ─────────────────   ──────────────────   ──────────────
  type                strategytype         modeltype
   │                   decisionresult      outputdata(模型分)
   ▼                   externalid=biz_id   strategydefid
  数据源配置
  s09_os_data_config
  code → name(数据源名)

关联键：
  biz_id = externalid（进件单号）
  executionid（一次风控执行批次）
  strategydefid（策略版本）→ model_record.strategydefid
  third.type = os_data_config.code（三方数据源）
```

**核心关联键**：
1. **biz_id / externalid**：进件单号，三张表都有关，用来串起一笔进件的完整链路
2. **executionid**：一次风控执行批次，策略和模型共用
3. **strategydefid**：策略版本，strategy_record 和 model_record 关联
4. **third.type = os_data_config.code**：三方请求和数据源配置关联

## 七、使用案例（实战 SQL）

### 案例1：看一笔进件的完整风控链路

```sql
-- 某进件单的风控全链路：策略 + 模型 + 三方数据
SELECT s.decisionresult, s.strategytype, s.strategydefid,
       m.modeltype, m.nodeserial, m.outputdata AS model_score,
       t.type AS third_type, substr(t.resp_body,1,200) AS third_resp
FROM ods.s21_risk_strategy_record s
LEFT JOIN ods.s21_risk_model_record m
    ON s.externalid = m.externalid AND s.strategydefid = m.strategydefid
LEFT JOIN ods.s09_third_request_record_log t
    ON s.externalid = t.biz_id
WHERE s.externalid = '1620000459564025'
  AND s.etl_date = '20260826'
```

### 案例2：统计正式策略的通过率（按月）

```sql
SELECT date_format(createtime, '%Y-%m') AS month,
       count(*) AS total,
       count_if(decisionresult = 'PASS') AS pass_cnt,
       count_if(decisionresult = 'PASS') * 1.0 / count(*) AS pass_rate
FROM ods.s21_risk_strategy_record
WHERE strategytype = 'CHAMPION'   -- 只取正式策略
  AND etl_date = (SELECT max(etl_date) FROM ods.s21_risk_strategy_record)
GROUP BY 1
```

### 案例3：看每个三方数据源的调用量

```sql
SELECT c.name, t.type, count(*) AS call_cnt
FROM ods.s09_third_request_record_log t
LEFT JOIN ods.s09_os_data_config c
    ON t.type = c.code AND c.del_flag = 0
WHERE t.etl_date = (SELECT max(etl_date) FROM ods.s09_third_request_record_log)
GROUP BY 1, 2
ORDER BY call_cnt DESC
```

### 案例4：把三方返回的模型分解析出来

```sql
-- resp_body 是 JSON，用 json_extract 提取
SELECT biz_id, type,
       json_extract_scalar(resp_body, '$.code') AS resp_code,
       json_extract_scalar(resp_body, '$.data.GD_X_32') AS multi_platform_score
FROM ods.s09_third_request_record_log
WHERE type = 78   -- advance 多平台
  AND etl_date = (SELECT max(etl_date) FROM ods.s09_third_request_record_log)
```

## 八、常见问题与注意点

| 问题 | 说明 |
|------|------|
| **必须带 etl_date** | 4张表都是分区表，不限定 etl_date 会全表扫描、极慢 |
| **CHAMPION vs SHADOW** | 分析决策结果只取 CHAMPION（正式），SHADOW 是影子测试 |
| **outputdata/resp_body 是 JSON** | 需要 json_extract 或程序解析才能用 |
| **type 要关联 os_data_config** | 三方请求的 type 是 code，不关联不知道是哪个数据源 |
| **一进件多模型** | model_record 里 nodeserial 递增，一个进件跑多个模型，别只取一行 |
| **executionid** | 同一笔进件一次完整风控共用，做链路分析用它串 |
